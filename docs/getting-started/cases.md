# Живые кейсы Bathys

Кейсы показывают полный цикл «запрос → инструменты Bathys → ответ агенту → профит»: что говорит человек или харнесс, какой инструмент выбирает агент и зачем, что возвращается и сколько это стоит. Футеры в примерах настоящие — они взяты из реальных вызовов, и по ним видно сжатие, кэш и время каждой операции. Сигналы футеров (`cache HIT`, `robots-refused`, `No results …`) расшифрованы в конце раздела C.

Кейсы раздела A инициирует человек, раздела B — агенты-специалисты, работающие автономно; раздел C учит харнесс работать эффективнее, D — держать эксплуатацию под контролем. Базовые конфиги и матрица выбора инструментов — в [integrate.md](integrate.md); полные гайды по харнессам — в [docs/integrations/](../integrations/overview.md).

## A. Пользовательские кейсы

### A1. Сравнение технологий под нагрузкой

**Запрос пользователя:**

> Сравни SQLite WAL и PostgreSQL для высоконагруженного чтения — что выбрать в 2026?

**Что делает агент:**

1. Формулирует запрос вопросом и вызывает `deep_research("SQLite WAL vs PostgreSQL read-heavy workload comparison 2026", max_sources=3)` — конвейер сам находит источники, параллельно читает топ-три и сливает дистиллят под запрос. Один вызов вместо цепочки «поиск + N чтений».
2. Разбирает дистиллят: термины из найденного (`page-level locking`, `MVCC`, `connection storms`) точнее бытовых формулировок — агент доуточняет ими второй заход и получает выверенную фактуру.
3. Верифицирует вывод по двум независимым источникам (`read_urls` по паре URL из выдачи) и собирает сравнение с URL на каждый ключевой факт.

```text
[bathys: 34 raw hits, top 8 considered · dove 3 pages · 35669 ch fetched → 7508 ch returned · 1.3s]
```

**Профит:** один вызов вместо N+1 — облачная квота не тратится вовсе; в контекст агента попадает 7.5k символов вместо ~35k, и он отвечает сравнением, а не пересказом выдачи.

### A2. Аудит спорного утверждения

**Запрос пользователя:**

> Проверь, правда ли что в Crawl4AI v0.7 упали latency-замеры.

**Что делает агент:**

1. Берёт стратегию `bathys_source_audit`: спорное утверждение проверяется по списку URL, а не по одному источнику.
2. Пакетно читает три ссылки из обсуждения через `read_urls([...], query="Crawl4AI v0.7 latency benchmarks change")` — битая ссылка останется строкой `(not fetched — …)`, а не сорвёт вызов.
3. Кросс-поиск опровержений: `web_search` по точной формулировке тезиса и `read_url` по найденным бенчмаркам — вердикт выносится по каждому тезису отдельно.

```text
[bathys: batch 3 urls · 3/3 ok · 268371 ch fetched → 1069 ch returned · 5.9s]
```

**Профит:** аудит пакетом стоит один вызов; агент возвращает верифицированный вердикт с URL на каждый пункт, а не «кажется, правда».

### A3. Свежий срез по теме

**Запрос пользователя:**

> Что нового в SearXNG за последние две недели?

**Что делает агент:**

1. Берёт стратегию `bathys_fresh_scan` и сужает окно свежести: `web_search("SearXNG release news", time_range=week)`.
2. Читает найденные страницы пакетом `read_urls` с `query="SearXNG changes last two weeks"` — дистиллят держит только новости, а не весь текст changelog'ов. Первый заход выходит из кэша (`cache HIT`), а в дистилляте — даты старше недели: один `refresh=true` на главный источник перезабирает его свежим, и сводка собирается с актуальными датами.
3. Финальная проверка повторным поиском уже выходит `MISS` — Bathys перезабрал данные из сети.

```text
[bathys: 6 hits · 3.7s · searx json 37541 ch → 1932 ch]
```

**Профит:** свежесть управляется параметром `time_range`, а не удачей; кэш честно подсказывает, когда источник стоит перечитать: `HIT` — возможно устаревшие данные, `MISS` — свежеполучено.

### A4. Статья под углом своего стека

**Запрос пользователя:**

> Прочитай эту статью и объясни, применимо ли к нашему стеку. *(даёт URL)*

**Что делает агент:**

1. Читает страницу прицельно: `read_url(url, query="применимость подхода к нашему стеку")` — дистиллятор BM25 оставляет пассажи, отвечающие на вопрос, а не пересказ статьи.
2. Если дистиллята не хватает, дочитывает смежный материал из той же выдачи; статья целиком в контекст не попадает.

```text
[bathys: page 17063 ch → 2325 ch · query-distilled · cache HIT · 0.0s]
```

**Профит:** 17k символов страницы сжимаются до 2.3k релевантных пассажей; JS-рендер не проблема — headless-chromium отдаёт текст там, где `curl` видит пустую страницу.

## B. Кейсы агентов-специалистов

Эти кейсы работают автономно: субагент [`bathys-researcher`](../../agents/bathys-researcher.md) и скиллы [`bathys-deep-dive`](../../agents/skills/bathys-deep-dive/SKILL.md) / [`bathys-source-audit`](../../agents/skills/bathys-source-audit/SKILL.md) выполняются внутри харнесса, человека в цикле нет. Установка — в гайдах [zcode](../integrations/zcode.md) и [Claude Code](../integrations/claude-code.md).

### B1. Код-ревьюер встречает незнакомую библиотеку

В PR используется библиотека, которой ревьюер не знает. Вместо прерывания работы разработчика он тихо вызывает `deep_research` по паттернам её использования и за минуту получает резюме практики сообщества.

**Профит:** ноль прерываний работы разработчика; комментарии к ревью доказательные — с URL на источник, а не «кажется, это антипаттерн».

### B2. Разработчик-агент попадает на экзотическую ошибку

Ошибка редкая, локальный контекст её не объясняет. Агент делает свежий срез: `bathys_fresh_scan` с `time_range=day` — issue-трекеры и форумы за последние сутки.

Результат — свежий воркаунд из первоисточника; если же ничего нет, агент получает честное `No results for: … · tried 3 engine sets` и говорит «не найдено», вместо того чтобы выдумывать решение.

**Профит:** решение из первоисточников, а не из галлюцинаций; пустая выдача — тоже результат, и агент отличает «не нашли» от «не искали».

### B3. QA-агент пишет тесты по мутировавшей доке

API задокументирован в новой версии, а тесты пишутся по старой. QA-агент прогоняет `bathys_source_audit` по changelog и доке, видит в футере `cache HIT` на доке, чей changelog уже ушёл вперёд, и перечитывает её с `refresh=true`.

**Профит:** тесты соответствуют текущей версии API, а не той, что агент помнил; сигнал `cache HIT` на протухших данных — повод для одного refresh, а не для недоверия кэшу в целом.

## C. Как научить харнесс работать с Bathys эффективно

Пошагово, без чтения остальных доков. Порядок — от «работает из коробки» к «работает идеально».

### Шаг 1. Подключить MCP-сервер

Блок `mcpServers` для вашего харнесса — в [integrate.md](integrate.md) и на странице конкретного клиента в [docs/integrations/](../integrations/overview.md).

### Шаг 2. Что получается из коробки

Ничего настраивать не нужно: на рукопожатии сервер сам отдаёт instructions-playbook (матрицу выбора инструментов и правила работы), annotations (человекочитаемые названия и хинты безопасности) и три стратегии-промпта — `bathys_deep_research`, `bathys_source_audit`, `bathys_fresh_scan`. Клиенты, которые показывают instructions, отдают playbook модели автоматически — агент уже знает, что ресёрч-вопрос — это `deep_research`, а не цикл `web_search` + `read_url`. Разбор — в [overview.md](../integrations/overview.md), раздел «Что даёт нативная интеграция».

### Шаг 3. Усилить: субагент, скиллы, дроп-ин

1. **Субагент.** Скопируйте профиль специалиста по глубокому ресёрчу:

   ```bash
   cp agents/bathys-researcher.md ~/.zcode/agents/     # zcode
   mkdir -p .claude/agents && cp agents/bathys-researcher.md .claude/agents/   # Claude Code
   ```

   Скиллы `agents/skills/bathys-deep-dive/` и `agents/skills/bathys-source-audit/` скопируйте в каталог скиллов харнесса. После этого глубокий ресёрч можно делегировать целиком — субагент работает только через Bathys.

2. **Дроп-ин.** Если харнесс не показывает MCP instructions модели, вставьте канонический блок из [`agents/HARNESS-DROPIN.md`](../../agents/HARNESS-DROPIN.md) в файл инструкций (`AGENTS.md`, `CLAUDE.md`, `.cursor/rules/*.mdc`). Блок самодостаточен: после него агент не ходит в интернет мимо инструментов Bathys.

### Шаг 4. Диагностировать по сигналам футеров

Футер каждого ответа — `[bathys: …]` — и специальные строки тела говорят агенту, что делать дальше:

| Симптом | Что передать агенту |
|---|---|
| `cache HIT`, но данные в дистилляте устарели (старые даты, версии) | один `refresh=true` на главный источник — не на весь пакет |
| `No results … · tried N engine sets` | движки капризничали и уже ретраились — сменить формулировку: синонимы, язык, `category` |
| `robots-refused` / `(not fetched — robots.txt …)` | сайт запретил чтение краулерам — уважать запрет и искать другой источник, не обход |
| `(not fetched — …)` на отдельной странице | источник не прочитан, но вызов не провален — работать с остальными секциями, недостающий URL добрать `read_url` |
| `Answer:` в выдаче | мгновенный справочный ответ SearXNG — годится как факт, спорное подтверждать источником |

Семантика сигналов — в профиле субагента [`agents/bathys-researcher.md`](../../agents/bathys-researcher.md) (раздел «Сигналы ответов»); контракт футеров — в [`docs/contracts/output-format.md`](../contracts/output-format.md).

## D. Базовая эксплуатация

Четыре процедуры, которых хватает большинству. Полный разбор — в [runbook.md](../operations/runbook.md).

**Проверка здоровья стека.** Один запуск проверяет конфиг, бэкенд-пинг, кэш и браузерный стек — MCP-сервер запускать не нужно:

```bash
.venv/bin/bathys-doctor
```

**Метрики за неделю.** Агрегатор считает сжатие, hit-rate и накопленную экономию из журнала `metrics.jsonl` — «токены сэкономлены» одной цифрой (`tokens_saved`):

```bash
.venv/bin/python scripts/metrics_report.py
```

**Очистка кэша.** Кэш — один файл SQLite; чистить нужно редко (после смены формата хранения или для освобождения места), протухшие записи игнорируются по TTL сами:

```bash
rm ~/.cache/bathys/cache.db    # предварительно остановите сервер и бэкенд
```

**Когда писать `refresh`.** Только при протухшем кэше: футер показывает `cache HIT`, а данные устарели. `refresh=true` форсит сеть и ломает кэш — «на всякий случай» его не передают.

**Brave-движок (опционально).** В нативном режиме Brave Search API включается одним env-ключом — движок `brave` появится в настройках SearXNG при следующей сборке:

```bash
export BATHYS_ENGINE_BRAVE_KEY=<ключ>
```

Таблица режимов — в [runbook.md](../operations/runbook.md); все 19 переменных `BATHYS_*` — в [configure.md](configure.md).
