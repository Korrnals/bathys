# Живые кейсы Bathys

Кейсы показывают полный цикл «запрос → инструменты Bathys → ответ агенту → профит»: что говорит человек или харнесс, какой инструмент выбирает агент, что возвращается и сколько это стоит. Футеры в примерах — из реальных вызовов: по ним видно сжатие, кэш и время каждой операции.

| Раздел | Кто действует | О чём |
|---|---|---|
| **[A](#a-пользовательские-кейсы)** | человек запрашивает | 4 кейса «запрос → инструменты → профит» |
| **[B](#b-кейсы-агентов-специалистов)** | агенты-специалисты, автономно | как субагент и скиллы работают без человека |
| **[C](#c-как-научить-харнесс-работать-с-bathys-эффективно)** | вы, один раз | подключить и научить харнесс работать эффективно |
| **[D](#d-базовая-эксплуатация)** | вы, по необходимости | doctor, метрики, кэш, refresh, Brave |

Базовые конфиги и матрица выбора инструментов — в [integrate.md](integrate.md); полные гайды по харнессам — в [docs/integrations/](../integrations/overview.md).

## A. Пользовательские кейсы

### 🧭 Кейс A1. Сравнение технологий под нагрузкой

> **Пользователь:**
> Сравни SQLite WAL и PostgreSQL для высоконагруженного чтения — что выбрать в 2026?

**Как идёт работа**

1. Агент формулирует запрос вопросом и вызывает `deep_research("SQLite WAL vs PostgreSQL read-heavy workload comparison 2026", max_sources=3)` — конвейер сам находит источники, параллельно читает топ-три и сливает дистиллят под запрос. Один вызов вместо цепочки «поиск + N чтений».
2. Разбирает дистиллят: термины из найденного (`page-level locking`, `MVCC`, `connection storms`) точнее бытовых формулировок — агент доуточняет ими второй заход и получает выверенную фактуру.
3. Верифицирует вывод по двум независимым источникам (`read_urls` по паре URL из выдачи) и собирает сравнение с URL на каждый ключевой факт.

```text
[bathys: 34 raw hits, top 8 considered · dove 3 pages · 35669 ch fetched → 7508 ch returned · 1.3s]
```

**Профит:** один вызов вместо N+1 — облачная квота не тратится вовсе; в контекст агента попадает 7.5k символов вместо ~35k, и он отвечает сравнением, а не пересказом выдачи.

---

### 🔍 Кейс A2. Аудит спорного утверждения

> **Пользователь:**
> Проверь, правда ли что в Crawl4AI v0.7 упали latency-замеры.

**Как идёт работа**

1. Агент берёт стратегию `bathys_source_audit`: спорное утверждение проверяется по списку URL, а не по одному источнику.
2. Пакетно читает три ссылки из обсуждения через `read_urls([...], query="Crawl4AI v0.7 latency benchmarks change")` — битая ссылка остаётся строкой `(not fetched — …)`, а не срывает вызов.
3. Кросс-поиск опровержений: `web_search` по точной формулировке тезиса и `read_url` по найденным бенчмаркам — вердикт выносится по каждому тезису отдельно.

```text
[bathys: batch 3 urls · 3/3 ok · 268371 ch fetched → 1069 ch returned · 5.9s]
```

**Профит:** аудит пакетом стоит один вызов; агент возвращает верифицированный вердикт с URL на каждый пункт, а не «кажется, правда».

---

### 📰 Кейс A3. Свежий срез по теме

> **Пользователь:**
> Что нового в SearXNG за последние две недели?

**Как идёт работа**

1. Агент берёт стратегию `bathys_fresh_scan` и сужает окно свежести: `web_search("SearXNG release news", time_range=week)`.
2. Читает найденное пакетом `read_urls` с `query="SearXNG changes last two weeks"` — дистиллят держит только новости, а не весь текст changelog'ов. Первый заход вышел из кэша (`cache HIT`), но в дистилляте даты старше недели: один `refresh=true` на главный источник перезабирает его свежим.
3. Финальная проверка повторным поиском выходит `MISS` — Bathys ходил в сеть.

```text
[bathys: 6 hits · 3.7s · searx json 37541 ch → 1932 ch]
```

**Профит:** свежесть управляется параметром `time_range`, а не удачей; кэш честно подсказывает, когда источник стоит перечитать: `HIT` — возможно устаревшие данные, `MISS` — свежеполучено.

---

### 📄 Кейс A4. Статья под углом своего стека

> **Пользователь:**
> Прочитай эту статью и объясни, применимо ли к нашему стеку. *(даёт URL)*

**Как идёт работа**

1. Агент читает страницу прицельно: `read_url(url, query="применимость подхода к нашему стеку")` — дистиллятор BM25 оставляет пассажи, отвечающие на вопрос, а не пересказ статьи.
2. Если дистиллята не хватает — дочитывает смежный материал из той же выдачи; статья целиком в контекст не попадает.

```text
[bathys: page 17063 ch → 2325 ch · query-distilled · cache HIT · 0.0s]
```

**Профит:** 17k символов страницы сжимаются до 2.3k релевантных пассажей; JS-рендер не проблема — headless-chromium отдаёт текст там, где `curl` видит пустую страницу.

## B. Кейсы агентов-специалистов

Эти кейсы автономны: субагент [`bathys-researcher`](../../agents/bathys-researcher.md) и скиллы [`bathys-deep-dive`](../../agents/skills/bathys-deep-dive/SKILL.md) / [`bathys-source-audit`](../../agents/skills/bathys-source-audit/SKILL.md) выполняются внутри харнесса, человека в цикле нет. Установка — в гайдах [zcode](../integrations/zcode.md) и [Claude Code](../integrations/claude-code.md).

### 🤖 B1. Код-ревьюер встречает незнакомую библиотеку

**Ситуация.** В PR — библиотека, которой ревьюер не знает.

**Действия агента.** Вместо прерывания работы разработчика ревьюер тихо вызывает `deep_research` по паттернам её использования и за минуту получает резюме практики сообщества.

**Профит.** Ноль прерываний работы разработчика; комментарии к ревью доказательные — с URL на источник, а не «кажется, это антипаттерн».

---

### 🤖 B2. Разработчик-агент попадает на экзотическую ошибку

**Ситуация.** Ошибка редкая, локальный контекст её не объясняет.

**Действия агента.** Свежий срез: `bathys_fresh_scan` с `time_range=day` — issue-трекеры и форумы за последние сутки.

**Профит.** Воркаунд из первоисточника; если ничего нет — честное `No results for: … · tried 3 engine sets`, и агент говорит «не найдено», вместо того чтобы выдумывать решение. Пустая выдача — тоже результат: агент отличает «не нашли» от «не искали».

---

### 🤖 B3. QA-агент пишет тесты по мутировавшей доке

**Ситуация.** API задокументирован в новой версии, а тесты пишутся по старой.

**Действия агента.** Прогоняет `bathys_source_audit` по changelog и доке; видит в футере `cache HIT` на доке, чей changelog уже ушёл вперёд, и перечитывает её с `refresh=true`.

**Профит.** Тесты соответствуют текущей версии API, а не той, что агент помнил; сигнал `cache HIT` на протухших данных — повод для одного refresh, а не для недоверия кэшу в целом.

## C. Как научить харнесс работать с Bathys эффективно

Четыре шага от «работает из коробки» к «работает идеально». Конфиги и тонкости по каждому клиенту — в [docs/integrations/](../integrations/overview.md).

### Шаг 1 — подключить MCP-сервер 🔌

Блок `mcpServers` для вашего харнесса — в [integrate.md](integrate.md) и на странице конкретного клиента в [docs/integrations/](../integrations/overview.md).

### Шаг 2 — что получается из коробки 📦

Ничего настраивать не нужно: на рукопожатии сервер сам отдаёт **instructions-playbook** (матрицу выбора инструментов и правила работы), **annotations** (человекочитаемые названия и хинты безопасности) и **три стратегии-промпта** — `bathys_deep_research`, `bathys_source_audit`, `bathys_fresh_scan`. Клиенты, которые показывают instructions, отдают playbook модели автоматически — агент уже знает, что ресёрч-вопрос — это `deep_research`, а не цикл `web_search` + `read_url`. Разбор — в [overview.md](../integrations/overview.md), раздел «Что даёт нативная интеграция».

### Шаг 3 — усилить: субагент, скиллы, дроп-ин 🚀

**Субагент.** Скопируйте профиль специалиста по глубокому ресёрчу:

```bash
cp agents/bathys-researcher.md ~/.zcode/agents/     # zcode
mkdir -p .claude/agents && cp agents/bathys-researcher.md .claude/agents/   # Claude Code
```

Скиллы `agents/skills/bathys-deep-dive/` и `agents/skills/bathys-source-audit/` скопируйте в каталог скиллов харнесса. После этого глубокий ресёрч можно делегировать целиком — субагент работает только через Bathys.

**Дроп-ин.** Если харнесс не показывает MCP instructions модели, вставьте канонический блок из [`agents/HARNESS-DROPIN.md`](../../agents/HARNESS-DROPIN.md) в файл инструкций (`AGENTS.md`, `CLAUDE.md`, `.cursor/rules/*.mdc`). Блок самодостаточен: после него агент не ходит в интернет мимо инструментов Bathys.

### Шаг 4 — диагностировать по сигналам футеров 🩺

Футер каждого ответа `[bathys: …]` и специальные строки тела говорят агенту, что делать дальше:

| Симптом | Что передать агенту |
|---|---|
| `cache HIT`, но данные устарели (старые даты, версии) | один `refresh=true` на главный источник — не на весь пакет |
| `No results … · tried N engine sets` | движки капризничали и уже ретраились — сменить формулировку: синонимы, язык, `category` |
| `robots-refused` | сайт запретил чтение краулерам — уважать запрет и искать другой источник, не обход |
| `(not fetched — …)` на отдельной странице | источник не прочитан, но вызов не провален — работать с остальными секциями, недостающий URL добрать `read_url` |
| `Answer:` в выдаче | мгновенный справочный ответ SearXNG — годится как факт, спорное подтверждать источником |

Семантика сигналов — в профиле субагента [`agents/bathys-researcher.md`](../../agents/bathys-researcher.md); контракт футеров — в [`docs/contracts/output-format.md`](../contracts/output-format.md).

## D. Базовая эксплуатация

Четыре процедуры, которых хватает большинству. Полный разбор — в [runbook.md](../operations/runbook.md).

### 🩺 Проверка здоровья стека

Один запуск проверяет конфиг, бэкенд-пинг, кэш и браузерный стек — MCP-сервер запускать не нужно:

```bash
.venv/bin/bathys-doctor
```

### 📊 Метрики за неделю

Агрегатор считает сжатие, hit-rate и накопленную экономию из журнала `metrics.jsonl` — «токены сэкономлены» одной цифрой:

```bash
.venv/bin/python scripts/metrics_report.py
```

### 🧹 Очистка кэша

Кэш — один файл SQLite; чистить нужно редко, протухшие записи игнорируются по TTL сами:

```bash
rm ~/.cache/bathys/cache.db    # предварительно остановите сервер и бэкенд
```

### ♻️ Когда писать `refresh`

Только при протухшем кэше: футер показывает `cache HIT`, а данные устарели. `refresh=true` форсит сеть и ломает кэш — «на всякий случай» его не передают.

### 🔑 Brave-движок (опционально)

В нативном режиме Brave Search API включается одним env-ключом — движок `brave` появится в настройках SearXNG при следующей сборке:

```bash
export BATHYS_ENGINE_BRAVE_KEY=<ключ>
```

Таблица режимов — в [runbook.md](../operations/runbook.md); все 19 переменных `BATHYS_*` — в [configure.md](configure.md).
