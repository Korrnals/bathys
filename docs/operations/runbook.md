# Runbook Bathys

Операционные процедуры для локального сервера Bathys. Конфигурация и значения env-переменных — в [configure.md](../getting-started/configure.md); словарь терминов — в [glossary.md](../meta/glossary.md).

## Ручной старт бэкенда

Обычно не нужен — автостарт поднимает бэкенд при первом поиске. Ручной старт пригодится, чтобы прогреть SearXNG до подключения клиента:

```bash
# любой путь установки: doctor с прогревом (см. «Диагностика»)
bathys-doctor --start-backend

# docker-режим из клона исходников: bundled compose.yaml (~/bathys — ваш клон)
docker compose -f ~/bathys/src/bathys/compose.yaml up -d

# нативный режим из клона: smoke соберёт и поднимет всё сам
.venv/bin/python scripts/smoke.py
```

## Останов бэкенда

| Режим | Команда / действие |
|---|---|
| Нативный | перезапустить MCP-клиент: при остановке сервера гасит и дочерний `searx.webapp`; точечно — `pkill -f "searx.webapp"` |
| Docker | `docker rm -f bathys-searxng` |
| Внешний инстанс | управляется тем, кто его поднял; Bathys его не трогает |

## Где логи

| Что | Где смотреть |
|---|---|
| Нативный SearXNG | `$BATHYS_SEARXNG_HOME/searxng.log` (дефолт `~/.local/share/bathys/searxng-home/searxng.log`) |
| Docker SearXNG | `docker logs bathys-searxng` (ротация 1 МБ × 1 файл задана в `compose.yaml`) |
| Сам Bathys | stderr клиента: строка запуска сервера и ошибки инструментов не пишутся в файлы |

## Очистка кэша

Кэш — один файл SQLite в `$BATHYS_CACHE_DIR` (дефолт `~/.cache/bathys/cache.db`).

```bash
pkill -f "searx.webapp"; docker rm -f bathys-searxng   # остановить бэкенд (по режиму)
rm ~/.cache/bathys/cache.db                            # удалить кэш
```

Останавливать сервер перед удалением нужно, чтобы не удалить файл под открытым дескриптором. Протухшие записи кэш игнорирует сам (по TTL), так что чистка нужна редко: после смены формата хранения или для освобождения места.

## Диагностика — `bathys-doctor`

Один запуск проверяет весь стек (MCP-сервер не нужен):

```bash
bathys-doctor          # конфиг, бэкенд-пинг, пин SHA, кэш, журнал метрик, crawl4ai-импорт
bathys-doctor --full   # то же + запуск headless-chromium (медленнее)
```

`--start-backend` поднимает бэкенд SearXNG **перед** проверкой:

```bash
bathys-doctor --start-backend   # прогреть стек до подключения клиента
```

Уместен, когда сервер ещё ни разу не запускался (свежая установка) и хочется увидеть зелёный `searxng backend` сразу, а не после первого вызова инструмента. Работает в режимах `auto`/`docker`/`native` — как обычный автостарт; при `BATHYS_AUTO_START=0` флаг игнорируется.

| Проверка | OK означает | FAIL — что делать |
|---|---|---|
| `config loads` | env прочитаны, значения собраны | смотреть сообщение об ошибке парсинга (`int`/`float` от пустой строки) |
| `searxng backend` | бэкенд отвечает JSON на пинг | сервер ещё не запускался — это норма, а не поломка: doctor без `--start-backend` бэкенд не поднимает и честно FAILит; поднимите его флагом или сделайте любой вызов инструмента |
| `searxng pin (F-302)` | маркер `.bathys-ref` совпадает с пином из `config.py` | native-дом в состоянии от другого ref — пересобрать |
| `cache db` | SQLite читается, живые строки посчитаны | файл повреждён — см. «Очистка кэша» |
| `metrics journal (F-304)` | журнал на месте (или `no events yet` — тоже OK) | — |
| `crawl4ai import` | браузерный стек импортируется | доставить зависимости: `playwright install-deps` |
| `chromium launch (--full)` | chromium стартует headless | `playwright install chromium` + системные библиотеки (см. аварию «Chromium не стартует») |

Exit-код для скриптов: `0` — все проверки прошли, `1` — есть хотя бы один FAIL. FAIL по бэкенду при незапущенном сервере означает «некому отвечать», а не поломку — это дефолт-поведение доктора (не врать, что всё хорошо), подсказка печатается сразу под строкой проверки.

## Снятие Bathys

Установка (однострочник, pip, npm, исходники — [install.md](../getting-started/install.md)) снимается симметричной командой:

```bash
bathys uninstall               # снять записи bathys со всех харнессов
bathys uninstall hermes zcode  # точечно (имена — как в `bathys install --list`)
```

Семантика:

- удаляются **только записи `bathys`** из конфигов харнессов — чужие серверы и остальной документ конфига не трогаются;
- каждая запись перед изменением копируется в бэкап: `<конфиг>.bathys-backup-<таймстамп>` (например `config.json.bathys-backup-20260908-120000`) рядом с конфигом;
- кэш и данные при снятии остаются на месте;
- субагент `bathys-researcher`, если ставился, — копия в каталоге харнесса (`~/.zcode/agents/` и т.п.), удаляется руками.

### `--purge` — полный снос

```bash
bathys uninstall --purge
```

Удаляет дополнительно: venv инсталлера (`~/.local/share/bathys/venv`), кэш (`~/.cache/bathys`), данные (`~/.local/share/bathys` — включая нативный SearXNG и журнал метрик). PATH-строку в `~/.profile` / `~/.bashrc` (одна строка с `bathys/venv/bin`) удалите руками — скрипт rc-файлы не редактирует.

### Восстановление из бэкапа

Бэкапы не удаляются ни `uninstall`, ни `--purge` — свежайший `*.bathys-backup-*` рядом с конфигом восстанавливается копированием обратно:

```bash
cp ~/.zcode/cli/config.json.bathys-backup-20260908-120000 ~/.zcode/cli/config.json
```

Затем перезапустите харнесс.

## Журнал метрик

С v0.4 каждый вызов инструмента пишет JSON-событие в `~/.local/share/bathys/metrics.jsonl` (путь — `$BATHYS_DATA_DIR/metrics.jsonl`): инструмент, кэш-флаг (`HIT`/`MISS`/`MIX`), `chars_in/out`, `secs`, `ok`, класс ошибки. Адреса и запросы не хранятся — только sha256-префиксы `url_hash`/`q_hash`.

Агрегатор считает hit-rate, медианное сжатие, p50/p95, ошибки и накопленный `tokens_saved`:

```bash
.venv/bin/python scripts/metrics_report.py                          # дефолтный путь
.venv/bin/python scripts/metrics_report.py путь/к/metrics.jsonl     # свой файл
```

Журнал отключается целиком переменной `BATHYS_METRICS=0` (потребуется рестарт процесса сервера). Методика, SLO и дашборд — в [metrics.md](metrics.md).

## API-движок Brave (опционально)

Brave Search API подключается к SearXNG одним ключом, поведение зависит от режима бэкенда:

| Режим | Как включить |
|---|---|
| Нативный | `BATHYS_ENGINE_BRAVE_KEY=<ключ>` — ключ попадает в генерируемые настройки SearXNG (`services.render_settings`), движок `brave` включается сам при следующей сборке дома |
| Docker | ключ не прокидывается — впишите движок `brave` с ключом в `searxng-settings.yml` контейнера руками и пересоздайте его |
| Внешний инстанс | управляет администратор инстанса; Bathys его настройки не меняет |

Live-проверка с реальным ключом — за мейнтейнером; переменная и семантика — в [config.md](../contracts/config.md).

## Типовые аварии

### Порт 8888 занят

Симптом: бэкенд не отвечает или стартует не тот процесс.

```bash
ss -ltnp | grep 8888   # кто слушает порт
```

Решение: если там чужой SearXNG — ничего не делайте, Bathys использует его как `external`. Если мусорный процесс — убейте его; либо уведите Bathys на другой порт (правка `port` в `src/bathys/searxng-settings.yml` и `compose.yaml` + `BATHYS_SEARXNG_URL`).

### SearXNG не отвечает

Симптом: первый поиск висит до `BATHYS_STARTUP_TIMEOUT` (90 c), затем ошибка с перечнем попыток `docker: …; native: …`.

```bash
tail -50 "$BATHYS_SEARXNG_HOME/searxng.log"   # или: docker logs bathys-searxng
```

Частые причины: первая сборка нативного режима ещё идёт (клон + зависимости — минуты; подождать или увеличить `BATHYS_STARTUP_TIMEOUT`); на внешнем инстансе выключен JSON API — поиск вернёт 403, включите `formats: [html, json]` (см. [configure.md](../getting-started/configure.md)).

### Chromium не стартует

Симптом: каждый `read_url` падает с ошибкой запуска браузера, при этом поиск работает.

Решение: на голой системе Chromium не хватает системных библиотек — доставьте их (`playwright install-deps` или пакеты `nss`, `nspr`, `atk`, `at-spi2-atk` и прочие по сообщению об ошибке в stderr клиента), затем проверьте `scripts/smoke.py`.

### Капчи поисковиков

Симптом: `web_search` возвращает мало хитов или пусто; в выдаче видны страницы-капчи.

Решение: снизьте частоту и подождите — блокировки домашнего IP отходят сами; смените `engines`/`category`, чтобы нагрузка ушла с заблокированного движка. Не обходим капчи агрессивно: прокси-пулы вне проекта (см. [charter.md](../product/charter.md), границы). Смягчение системно и уже в коде с v0.2 — вежливые задержки (`BATHYS_SEARCH_MIN_INTERVAL`) и ретраи с ротацией наборов движков и нарастающими паузами ([roadmap.md](../product/roadmap.md)).

### `robots-refused` в ответе

Симптом: `read_url` возвращает пустое тело с пометкой и футером `[bathys: page 0 ch → 0 ch · robots-refused · cache MISS · …]`.

Это не ошибка: с v0.4 прямые нырки страниц уважают robots.txt хоста (`Disallow: /` — отказ). Поиск не затрагивается, недоступный robots.txt трактуется как разрешение (fail-open), отказ кэшируется на час. Если сценарий требует игнорировать robots — `BATHYS_ROBOTS=0` и рестарт сервера.

### Кэш отдаёт устаревшее

Симптом: страница изменилась, а `read_url` возвращает старый текст с `cache HIT`.

Решение: живая страница протухнет по `BATHYS_PAGE_TTL` (сутки); для немедленного обновления передайте `refresh=true` — вызов уйдёт в сеть мимо кэша и перезапишет запись (есть у всех четырёх инструментов). Крайняя мера — очистить кэш целиком (см. выше).
