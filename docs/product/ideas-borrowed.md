# Заимствованные идеи: pi-web-access → Bathys

| Поле | Значение |
|---|---|
| Источник | [pi-web-access](https://github.com/nicobailon/pi-web-access) (Pi coding agent extension, 1399★, активен 2026-09) — разведано живьём через Bathys 2026-09-09 |
| Принцип | Реализация всегда наша; заимствуются **проверенные продуктовой практикой** решения. Pi — Extension для агента (TypeScript, полный системный доступ), Bathys — единый локальный поисковый сервис (MCP, слой данных). Контексты разные — переносим только то, что усиливает наш конвейер, не ломая хартию (без LLM внутри, без облака по умолчанию). |
| Статус | Кандидаты в роадмап; приоритизация ниже |

## Что переносим (сильные идеи, ранжировано)

### 1. `source_check` — верификация утверждения как machine-readable артефакт ★★★

У них: `source_check({claim, queries?, fetchContent?, domainFilter?})` → артефакт: статус `supported | contradicted | unclear | missing-evidence`, цитаты пассажей с оффсетами, SHA-256 хэши контента, качество источников; **ошибки поиска/фетча остаются в артефекте, не выбрасываются молча**.

Почему нам: у Bathys уже есть промпт `bathys_source_audit` (текстовая стратегия) и скилл — но статус-вердикты у вызывающего агента остаются текстом, который модель может исказить. Детерминированная часть (сбор источников, пассажи с оффсетами, хэши, «1 источник vs 2 независимых») может считать **движок Bathys** — вердикты `supported/contradicted` по правилу «2 независимых домена» — а синтез остаётся агенту. Это углубление нашего же принципа «слой данных без LLM»: верификация фактуры детерминирована, интерпретация — у харнесса.

Реализация: новый инструмент `source_check` (5-й) ИЛИ расширение `read_urls` параметром `claim`; артефакт — наш строковый формат с блоками `[bathys: …]`-статистикой.

### 2. `get_search_content` — пагинация по кэшу с `findText` ★★★

У них: сохранённый контент извлекается позже по `responseId` с `offset/limit` или `findText` (exact/case-insensitive/fuzzy, кап 20k, счётчики совпадений и контекст).

Почему нам: у Bathys кэш сырца **уже есть** (до дистилляции — это наше преимущество), но агент может получить только повторный дистиллят. Дать `find_text(url, pattern)` — поиск по сырому кэшу без сети: «найди в той статье точную цитату про X». Дёшево (кэш уже лежит), идеально для аудита и точных цитат.

Реализация: параметр `find` в `read_url` при cache-HIT или отдельный инструмент; поиск по сырому тексту с контекстом ±N символов.

### 3. GitHub-специализация: клон вместо скрейпа ★★

У них: GitHub-URL → локальный `git clone` (кэш на сессию, >350MB → API-вид); PR/issue → приоритизированный markdown-документ (статус, чеки, ревью, комменты, `gh`-CLI) вместо HTML-скрейпа.

Почему нам: наш HTTP-ярус на GitHub получает HTML-мусор, браузерный — тяжёлый. Спец-обработчик GitHub-URL (детект по хосту) → `gh api` для PR/issues (структура, а не парсинг) и README+дерево для репо — это **та же двухъярусная философия, но ярус-1 специализируется по типу URL**. `gh` уже есть в системе; без `gh` — фолбэк на HTTP-ярус.

Реализация: в `crawler._fetch_http` — редирект на GitHub-ветку (детект: github.com/{owner}/{repo}[/pull|/issues/|N]).

### 4. PDF → Markdown-конверсия ★★

У них: PDF-URL → конверсия и сохранение в temp-каталог (агент читает секции `read`-ом, не грузя весь документ в контекст); три движка: datalab (layout-aware), gemini (LLM), unpdf (локально, без ключа).

Почему нам: OCR-инициатива у нас **приостановлена** (VLM = GPU-боль), но unpdf-путь — это **локальная конверсия текстовых PDF без ML** (`pip install pymupdf` уже был в плане OCR-инициативы как text-layer). Наш двухъярусный HTTP-ярус сейчас на PDF просто падает («unsupported content-type» — сам видел в коде). Текстовый PDF без ML — честное закрытие 80% PDF-кейса без разморозки OCR.

Реализация: детект `content-type: application/pdf` в HTTP-ярусе → pymupdf → текст в тот же конвейер дистилляции. Сканы — честный отказ с указанием на OCR-инициативу.

### 5. Routing/fallback-конфигурация ★ (у нас уже частично есть)

У них: `searchRouting: {providers: [...], fallbackOn: [transient, quota, network, invalid-response]}` — типизированные причины фолбэка; `provider: "all"` — параллельный мульти-поиск; `proxy` per-call.

Что берём: (а) **типизация причин фолбэка** — наш F-101 ретраится по «пустой выдаче», но не различает `captcha` vs `timeout` vs `quota` на уровне retry-решения (unresponsive_engines это содержит! — парсить причину); (б) `provider: "all"`-режим для `web_search` — параллельный опрос всех активных движков с дедупликацией (у SearXNG это уже есть в `!format=json` — нам нужно просто НЕ передавать engines и объединить) — **дешёво, у нас почти есть**.

Не берём: их 25+ облачных провайдеров (против нашей хартии), browser-cookies Gemini Web (приватность-риск, у нас robots-этика), curator-UI (UI = Not-doing).

## Чего НЕ заимствуем (и почему — зафиксировано)

| Их фича | Почему нет |
|---|---|
| Video understanding (YouTube/Gemini/frames) | Требует облачной VLM (Gemini) — против «ноль облака по умолчанию»; локального аналога без GPU нет |
| 25+ облачных поисковых провайдеров | Наша ценность — оркестрация локального SearXNG; облако — только опциональные ключи (archcom #4) |
| Browser-cookie авторизация (Gemini Web) | Приватность-антипаттерн для нашего позиционирования |
| Curator-UI (браузерный) | UI = Not-doing хартии |
| LLM-суммаризация результатов | «LLM внутри нет» — синтез у вызывающего агента |
