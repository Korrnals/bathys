## 1. Проблема

Агентные среды (ZCode и подобные) списывают квоту подписки за каждый вызов облачного
MCP-инструмента. Типовой цикл веб-ресёрча — «поиск → чтение трёх-пяти страниц → повтор
с уточнением» — умножает списания на каждой итерации: агент платит не за результат,
а за сам факт обращения к облаку. Bathys заменяет этот цикл локальным конвейером,
который не тратит подписку вовсе.

### Кто ест квоты

| Облачный инструмент | Как съедает квоту подписки | Чем заменяет его Bathys |
|---|---|---|
| Облачный `web-search` MCP | Списывает ~1% месячной квоты за один запрос (по данным статьи на Infostart) | Выполняет метапоиск локально через SearXNG и возвращает сжатый список ссылок |
| Облачный `web-reader` / page fetch | Списывает за каждую прочитанную страницу и режет контент на своей стороне | Рендерит страницу собственным headless-Chromium (Crawl4AI) и отдаёт дистиллированный текст |
| `vision` / облачный extract | Списывает за скриншот или структурированное извлечение | Отдаёт чистый Markdown, который модель читает как обычный текст |

Мотивация мейнтейнера — локальный аналог Tavily/Firecrawl по роли, но не по устройству:
Bathys — единый локальный поисковый сервис глубокого ресёрча для ИИ-агентов, а не
связка двух сервисов (аналогия: БД не «обёртка над B-tree»). SearXNG (метапоиск,
70+ движков, приватность) и Crawl4AI (извлечение контента JS-страниц) работают внутри
как сменные движки двух ступеней конвейера; стратегию — что искать, что читать,
сколько вернуть — ведёт сам Bathys и сам поднимает свой бэкенд.

## 2. Миссия

Bathys — единый локальный поисковый сервис глубокого ресёрча для ИИ-агентов: один
процесс, свой конвейер (метапоиск → извлечение → дистилляция под запрос → кэш →
метрики) и собственный интерфейс из четырёх инструментов. SearXNG и Crawl4AI внутри —
сменные движки двух ступеней конвейера, а не «сервисы, которые мы оборачиваем»:
Bathys владеет стратегией (что искать, что читать, сколько вернуть), они — только
исполнительной механикой.

Служебная цель конвейера — давать LLM-агенту веб-факты за минимальное число токенов
и вызовов: без облачных квот, без отправки запросов третьим сторонам сверх самих
поисковых движков.

Свои возможности уровня продукта, которых нет ни у SearXNG, ни у Crawl4AI по
отдельности: query-дистилляция BM25 с жёсткими бюджетами, кэш сырца до дистилляции
(пере-дистилляция бесплатно), живучесть к блокировкам (ретраи с паузами + здоровье
движков), robots-этика, пакетное чтение с перераспределением бюджета, JSON-режим,
журнал метрик, doctor, самоподъём бэкенда в 3 режимах.

## 3. Jobs to be done

Работа агента в интернете через Bathys — нативная: веб-ресёрч перестаёт быть цепочкой
внешних платных вызовов и становится обращением к локальному сервису, как запрос к БД.

1. **Ресёрч одним вызовом.** Когда я прошу агента исследовать вопрос, я хочу получить
   дистиллят топ-источников одним вызовом `deep_research`, чтобы конвейер «поиск →
   чтение → дистилляция» отработал внутри Bathys, а не растягивался на цепочку
   облачных «`web-search` + N чтений страниц» с квотой за каждым шагом.
2. **Чтение JS-страниц.** Когда нужная страница рендерится JavaScript, я хочу получить
   чистый Markdown её содержимого, чтобы модель читала суть, а не скрипты, навигацию
   и рекламу.
3. **Повтор без повторной платы.** Когда я повторяю запрос или перечитываю ту же
   страницу под другим углом, я хочу мгновенный ответ из кэша сырца, чтобы
   пере-дистилляция не стоила ни сети, ни токенов.

## 4. Границы проекта

### В объёме (scope in)

- Метапоиск (движок SearXNG внутри — сменный) с фильтрами `time_range` / `category` / `language` / `engines`.
- Чтение и JS-рендер страниц (движок Crawl4AI внутри — сменный) общим headless-браузером.
- Дистилляция текста под запрос (`slim_markdown` + BM25-пассажи) с жёстким бюджетом символов.
- TTL-кэш поисков и страниц (SQLite); сырец кэшируется до дистилляции.
- Живучесть к блокировкам: ретраи с нарастающими паузами, здоровье движков, вежливый темп.
- Автостарт поискового бэкенда (SearXNG) в трёх режимах: внешний инстанс → docker compose → нативный.
- MCP-интерфейс из четырёх инструментов (`deep_research`, `web_search`, `read_url`, `read_urls`).
- Встроенный агент-специалист (инструкции + скиллы + MCP-промпты), исполняется вызывающим харнессом.
- Футеры-статистика сжатия и cache HIT/MISS в каждом ответе.

### Вне объёма (scope out)

- **Локальная LLM, синтез отчёта, multi-hop логика** — это работа вызывающей модели
  (осознанный отказ от конкуренции с Perplexica).
- **Свой поисковый индекс** — Bathys всегда ищет в реальном времени через метапоиск.
- **UI** (веб-интерфейс, чат, панель) — Bathys безголовый сервис с собственным
  интерфейсом четырёх инструментов.
- Прокси-пулы и агрессивный обход капч — допускается только вежливая клиентская гигиена.
- Обязательные облачные сервисы — опциональные API-движки допускаются, но выключены по умолчанию.
- Внешняя телеметрия — любые метрики остаются локальными.

## 5. Принципы

1. **Токен-экономика прежде всего.** Каждый байт ответа должен быть оправдан запросом:
   сжатие измеряется, показывается в футерах и проверяется критериями успеха.
2. **Продукт владеет стратегией, движки сменные.** Bathys решает, что искать, что
   читать и сколько вернуть; SearXNG и Crawl4AI — внутренние сменные движки двух
   ступеней конвейера (метапоиск и извлечение), а не «сервисы, которые мы
   оборачиваем». Замена движка не меняет ни интерфейс, ни стратегию.
3. **Без LLM внутри.** Bathys ищет, извлекает, чистит, дистиллирует и кэширует.
   Синтез, выводы и multi-hop планирование остаются за вызывающей моделью;
   агент-специалист поставляется как инструкции и скиллы для харнессов
   (agents/ + MCP-промпты), а не как встроенная модель.
4. **Ноль обязательных облачных зависимостей.** Весь стек живёт на локальной машине;
   платное API — только осознанная опция, никогда — требование.
5. **Единый сервис с самоподъёмом бэкенда.** Один процесс решает всё: поисковый
   бэкенд (SearXNG) поднимается сам (`external` → `docker` → `native`), без ручных
   шагов установки.

## 6. Критерии успеха

**Главная метрика**: медианное сжатие — доля возвращённых агенту символов от сырых,
полученных из сети, **не выше 10%** на типовом ресёрче (то есть экономия ≥ 90%).
Базовые замеры, подтверждающие достижимость: поиск 37k → 511 токенов (~98%),
страница 17k → 581 токенов (~97%), `deep_research` 35k → 7k токенов за 3,2 с
(холодный старт), повторы из кэша — 0,0 с.

| Метрика | Как измеряем | Цель | Где учитывается |
|---|---|---|---|
| Сжатие токенов (главная) | Сравниваем сырые символы источника и символы ответа по футерам | ≥ 90% экономии на типовом ресёрче | `docs/operations/metrics.md` (нужен документ) |
| Доля кэш-хитов | Считаем cache HIT/MISS из футеров за неделю использования | ≥ 40% на повторных сессиях | `docs/operations/metrics.md` |
| Успешность поиска | Считаем долю вызовов, вернувших ≥ 1 непустой хит | ≥ 90% за недельный прогон | `docs/operations/metrics.md` |
| Задержка глубокого ресёрча | Меряем холодный `deep_research` (3 источника) секундомером | p95 ≤ 30 с на домашнем канале | `docs/operations/metrics.md` |

## 7. Риски

| Риск | Почему это важно | Как отвечаем |
|---|---|---|
| Капчи поисковиков при агрессивной частоте с домашнего IP | Главный продуктовый риск: без смягчения выдача деградирует до пустой | Ротация движков, вежливые задержки, приоритет API-движков (см. [roadmap.md](roadmap.md), v0.2/v0.4) |
| Нет своего индекса | Качество и скорость зависят от живых поисковиков в момент запроса | Честно позиционируем (см. [competitive.md](competitive.md)); улучшаем устойчивость, не обещаем индекс |
| Supply-chain: нативный режим клонирует `master` SearXNG | Изменение в апстриме может сломать или скомпрометировать бэкенд | Переходим на пин проверенного тега релиза (F-302) |
| Chromium держит память и иногда падает на тяжёлых страницах | Агент получает ошибку чтения | Ошибки страниц кэшируются, `deep_research` деградирует до сниппета, а не падает целиком |
| Формат JSON-выдачи SearXNG требует ручного включения на внешних инстансах | Внешний режим отвечает 403 без подсказки | Клиент уже подсказывает включить `search.formats: [html, json]` при 403 |
