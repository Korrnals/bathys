# ADR 0006 — Три инструмента, вывод — готовые к показу строки

> **Примечание (0.4.0–0.5.0):** исторически решение принималось для трёх
> инструментов; `read_urls` (v0.2) расширил поверхность до четырёх без смены
> принципа «минимальная поверхность, строковый вывод». Формулировка
> «инструмент добавляется только если он сокращает вызовы или токены»
> остаётся критерием приёма новых инструментов.

| Поле | Значение |
|---|---|
| Статус | Accepted (расширен read_urls в v0.2) |
| Дата | 2026-09-06 |
| Применимо к | Bathys v0.1.0 |
| Затрагивает | `src/bathys/server.py`, `src/bathys/core.py` |

## Context

Каждый инструмент MCP-сервера оплачивается дважды: схемой в `tools/list` (контекст каждой сессии) и токенами ответа (контекст каждого вызова). Потребитель Bathys — LLM-агент: результат читает модель, а не код, поэтому JSON-обвязка в ответе — чистый расход. Транспорт — локальные клиенты, у которых родной канал — stdio.

## Decision

Ровно три инструмента, закрывающих три глагола ресёрча, с выводом в виде готовых к показу строк (грамматики — `docs/contracts/output-format.md`, параметров — `docs/contracts/mcp-tools.md`):

| Инструмент | Глагол | Возврат |
|---|---|---|
| `deep_research(query, …)` | найти и прочитать | дайджест: `Answer:` + секции источников + футер |
| `web_search(query, …)` | найти ссылки | ранжированный список `N. title / url / snippet` + `Answer:`/`Refine:` + футер |
| `read_url(url, query?, …)` | прочитать страницу | заголовок + дистиллированный markdown + футер |

Каждый ответ завершается футером `[bathys: …]` со статистикой (hits, HIT/MISS, in/out, секунды) — машиночитаемым хвостом для метрик без отдельного протокола.

Транспорт — `stdio` (`mcp.run(transport="stdio")`); stdout строго для протокола, логи библиотек уходят на stderr/в файлы (`_hush_stdout_logs`, лог нативного SearXNG — в `searxng.log`).

## Alternatives

| Альтернатива | Почему отклонена |
|---|---|
| JSON-структуры в ответах | больше токенов на скобки, кавычки и экранирование; модель всё равно читает текст |
| Зоопарк мелких инструментов | каждая лишняя схема живёт в контексте каждой сессии; различие «search vs research» дешевле сделать параметрами одного вызова |
| HTTP-транспорт | нужен stdio для локальных клиентов (Claude Desktop, ZCode и пр.); сетевой слой добавил бы аутентификацию без новой пользы |

## Consequences

- Положительные: минимальная поверхность схемы; один вызов `deep_research` заменяет связку search+read; футеры дают метрики задаром (`docs/operations/metrics.md` §3.1).
- Отрицательные: парсинг структурированных полей клиентом-кодом невозможен без расчёта на футер-грамматику (компенсируется политикой совместимости в `output-format.md`); добавление нового инструмента — ломкое изменение поверхности, требует отдельного решения.
